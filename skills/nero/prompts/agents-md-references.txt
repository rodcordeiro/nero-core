Use obrigatoriamente a skill $nero.

Objetivo:
Atualizar ou criar `AGENTS.md` no repositorio da aplicacao em checkout, deixando-o o mais enxuto possivel, e mover detalhes para `.agents/references/`, estruturando em pastas quando isso otimizar a leitura.

Parametros:
- `<REPO_APP>`: caminho local do repositorio da aplicacao
- `<NOME_DO_PROJETO>`: nome canonico no Knowledge Repo (se conhecido; ex.: `Acme.Api`)
- `<DOMINIO>`: `api` | `front` | `mobile` | `integracoes` (inferir se nao informado)

Premissas:
- Nao alterar codigo de produto (controllers, services, screens, workers, DI, pipelines), salvo pedido explicito do usuario.
- `AGENTS.md` e indice operacional para agentes: identidade + roteamento + regras rapidas.
- Detalhes vao para `.agents/references/` em arquivos curtos, uma responsabilidade por arquivo.
- Preferir ler so o arquivo da tarefa; evitar monolitico.
- Validar no filesystem o estado real do repo antes de escrever (README, entrypoint, estrutura, docs existentes).
- Nao inventar regra de negocio; sem evidencia, omitir ou marcar como hipotese.
- Nunca registrar secrets, tokens, cookies, Authorization, URLs sensiveis, payloads sensiveis ou valores reais de ambiente.
- Se ja existir `AGENTS.md` / `.agents/`, refatorar e deduplicar; nao clonar conteudo.
- Guidelines de dominio vivem na skill `$nero` (`references/guidelines/`); nao copiar o texto integral para o repo da app — so aplicar e apontar.
- Domain Skills de produto/lib ficam fora do Nero; ver `references/domain-skills.md`.

---

## 1) Classificar o projeto

1. Inferir dominio primario a partir do nome/stack/estrutura:
   - API .NET / Nest / similar → `api`
   - Next/React web → `front`
   - Expo/React Native → `mobile`
   - Hub/barramento/integracao central → `integracoes` (ou segundo dominio quando couber)
2. Mapear entrypoint, stack, fronteiras e areas de risco sem editar codigo.
3. Opcional (se MCP disponivel): `nero_get_project_context` / `nero_search_knowledge` para precedentes de docs de agentes no Knowledge Repo.

## 2) Estrutura alvo

Adaptar ao tamanho do projeto. Minimo:

```text
AGENTS.md
.agents/references/
  index.md
  structure.md          # pastas/modulos/camadas (factual do checkout)
  runtime.md            # boot, DI, pipeline, hosted services / app bootstrap
  domain.md             # areas de negocio / proposito
  conventions.md        # regras praticas de mudanca e teste
  patterns.md           # padroes locais observados
  tech-debt.md          # divida e prioridades (inclui gaps vs guideline, se houver)
```

Usar pastas quando houver volume ou multiplos fluxos:

```text
.agents/references/
  index.md
  structure.md
  runtime.md
  domain.md
  conventions.md
  patterns.md
  tech-debt.md
  flows/
    <flujo-a>.md
    <flujo-b>.md
  screens/                 # front/mobile com varias superficies
    <area>.md
```

Regras de pastas:
- Criar `flows/` so se houver >1 fluxo operacional relevante.
- Criar `screens/` (ou equivalente) so em front/mobile com multiplas areas de UI.
- Nao criar pasta/arquivo vazio “por simetria”.
- `index.md` deve mapear “quando ler o que”, incluindo o ponteiro do guideline `$nero`.

## 3) Conteudo do AGENTS.md

Manter curto. Incluir apenas:

1. Identidade minima (nome, stack, arquitetura/estilo, entry).
2. Tabela “Como usar este contexto” apontando para `.agents/references/` **e** para o guideline do dominio em `$nero` (`references/guidelines/...`).
3. Regras rapidas (mudancas localizadas, testes, comando de validacao do projeto).
4. Skills condicionais (secao 4).

Nao repetir nos references o que ja esta no AGENTS, e vice-versa.
Nao colar o texto do guideline no AGENTS — so o ponteiro + 1–3 regras locais derivadas do checkout.

## 4) Skills e guidelines condicionais (obrigatorio avaliar)

### 4.0 Mapa dominio → guideline (espelho de 1.1)

| Dominio | Skill guideline path |
|---|---|
| `api` | `$nero` → `references/guidelines/api-guidelines.md` |
| `integracoes` | `$nero` → `references/guidelines/api-guidelines.md` (heranca) |
| `front` | `$nero` → `references/guidelines/front-guidelines.md` |
| `mobile` | `$nero` → `references/guidelines/mobile-guidelines.md` |

Sempre refletir o ponteiro no `AGENTS.md` e em `references/index.md`.

### 4.1 Integracoes / hubs / messaging

Se o repositorio for API ou hub de integracao (`dominio=api` ou `integracoes`, ou evidencia de consumer/producer — inbox, assinaturas, fila, topico/evento/entidade/versao):

- Incluir no `AGENTS.md` (tabela e regras rapidas) e espelhar em `references/index.md` + `conventions.md` a Domain Skill do time **somente se existir e houver evidencia** (ver `references/domain-skills.md`).
- Nao expandir o fluxo do hub dentro do AGENTS; a Domain Skill e a fonte operacional do produto.

Se o repo **nao** for API/hub e nao consumir/publicar mensagens: omitir a regra (nao forcar).

### 4.2 Outras Domain Skills e skills de framework

Acionar/documentar no AGENTS somente com evidencia no checkout:

| Condicao | Skill |
|---|---|
| Lib/auth/UI kit interna do time (package/import comprovado) | Domain Skill local do time (fora do Nero) |
| Projeto mobile RN/Expo | skills RN/Expo aplicaveis + `$nero` |
| Sem evidencia | omitir |

Nao assumir skills de components/auth/hub embutidas no Nero — elas nao fazem parte do canônico.

## 5) Qualidade e anti-padroes

- Arquivos enxutos; preferir listas e tabelas a prosa longa.
- Evidencia concreta (paths, comportamentos observados).
- Remover duplicacoes e secoes historicas irrelevantes.
- Distinguir caminho **ativo** vs helper/comentario/legado quando documentar workers/integracoes.
- README desatualizado nao prevalece sobre o codigo.
- Guideline da skill nao substitui o inventario do checkout; nao inventar pastas “do guideline” que nao existem.

## 6) Knowledge (opcional, se houver aprendizado reutilizavel)

Se o padrao de AGENTS/references for novo ou evoluir de forma reutilizavel:

1. Registrar via MCP (`nero_register_pattern` / `nero_register_snapshot`) no escopo adequado (`project` local; `domain`/`global` so com evidencia de reuso).
2. Apos o lote: `nero_admin_reindex` → `nero_admin_validate` (`isValid=true` e `isCompliant=true`) → commit/push apenas do Knowledge Repo se houver alteracao.

Nao e obrigatorio registrar knowledge em todo run deste playbook.
