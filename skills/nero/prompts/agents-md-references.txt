Use obrigatoriamente a skill $nero.

Objetivo:
Atualizar ou criar `AGENTS.md` no repositorio da aplicacao em checkout, deixando-o o mais enxuto possivel, e mover detalhes para `.agents/references/`, estruturando em pastas quando isso otimizar a leitura.

Parametros:
- `<REPO_APP>`: caminho local do repositorio da aplicacao
- `<NOME_DO_PROJETO>`: nome canonico no Knowledge Repo (se conhecido; ex.: `Acme.Api`)
- `<DOMINIO>`: `api` | `front` | `mobile` | `integracoes` | `powershell` | `mcp` (inferir se nao informado)

Guardrails:
- Escopo: so `AGENTS.md` e `.agents/references/` (codigo de produto so com pedido explicito).
- `AGENTS.md` e indice: identidade + roteamento + regras rapidas. Detalhe vive num arquivo de uma responsabilidade.
- Checkout vence: validar README, entrypoint, estrutura e docs no filesystem antes de escrever; README desatualizado cede ao codigo.
- Registrar so o comprovado; sem evidencia, omitir ou marcar hipotese.
- Secrets, tokens, cookies, Authorization, URLs/payloads sensiveis e valores reais de ambiente ficam fora de docs e notes.
- Se ja existir `AGENTS.md` / `.agents/`, refatorar e deduplicar.
- Guidelines de dominio: ler em `$nero` → `references/guidelines/`; no app, so ponteiro + 1–3 regras locais do checkout.
- Domain Skills de produto/lib: fora do Nero; `references/domain-skills.md`.
- Arquivos enxutos: listas e tabelas. Distinguir caminho ativo vs helper/legado.
- `structure.md` lista so o que existe no checkout (pastas do guideline ausentes viram debito, nao arvore inventada).

## 1) Classificar o projeto

Done when: `<DOMINIO>` escolhido, entrypoint/stack nomeados, e a evidencia (path ou arquivo) citada.

Inferir dominio primario a partir do nome/stack/estrutura:

| Evidencia | Dominio |
|---|---|
| API .NET / Nest / similar | `api` |
| Next/React web | `front` |
| Expo/React Native | `mobile` |

| Modulo PowerShell (`*.psd1`/`*.psm1`) ou scripts `.ps1`/`.bat`/`.cmd`/`.vbs` | `powershell` |
| Servidor/cliente MCP (SDK, host .NET, tools/resources/prompts, stdio/HTTP) | `mcp` |

Mapear entrypoint, stack, fronteiras e areas de risco. Opcional (MCP): `nero_get_project_context` / `nero_search_knowledge` para precedentes de docs de agentes.

## 2) Aplicar o guideline do dominio

Done when: o guideline foi lido; o ponteiro esta no plano de AGENTS/index; gaps vs checkout estao em `tech-debt.md` ou explicitamente ausentes.

| Dominio | Guideline (`$nero`) |
|---|---|
| `api` | `references/guidelines/api-guidelines.md` |
| `integracoes` | `references/guidelines/api-guidelines.md` (heranca; anotar no AGENTS/index) |
| `front` | `references/guidelines/front-guidelines.md` |
| `mobile` | `references/guidelines/mobile-guidelines.md` |
| `powershell` | `references/guidelines/powershell-guidelines.md` |
| `mcp` | `references/guidelines/mcp-guidelines.md` |

Aplicacao:
1. O guideline orienta estrutura esperada, regras, comandos, estilo, testes e seguranca.
2. `structure.md` / `conventions.md` descrevem o que existe no checkout.
3. Divergencia vs alvo do guideline → item em `tech-debt.md`. Reestruturar codigo fica fora deste playbook.
4. Ponteiro na tabela "Como usar este contexto" e em `references/index.md`: dominio X → `$nero` → `references/guidelines/<arquivo>`.

Prioridade por dominio (alem de ler o guideline):

| Dominio | Foco no checkout |
|---|---|
| `api` | Fronteiras Controller/Service/Repository/DTO (ou Nest), contratos publicos, migrations/jobs/consumers |
| `integracoes` | Igual `api`, mais heranca explicita do guideline de API |
| `front` | Rotas/pages finas, hooks/services de feature, design system existente, estados loading/empty/error |
| `mobile` | Layout real vs Expo esperado no guideline; debitar gaps; skills RN/Expo na secao condicional |
| `powershell` | Manifesto/modulo/exports/help; scripts ativos vs legado; riscos de maquina/rede/registro/servicos |
| `mcp` | Entrypoint, transport, capabilities, schemas, config, seguranca; consumidor MCP: registrar como consumidor, sem comportamento de servidor sem evidencia |

## 3) Estrutura alvo

Done when: a arvore escolhida existe no plano, cada arquivo tem uma responsabilidade, e pastas extras tem justificativa de volume.

Minimo:

```text
AGENTS.md
.agents/references/
  index.md              # quando ler o que, incluindo o ponteiro do guideline `$nero`
  structure.md          # pastas/modulos/camadas (factual do checkout)
  runtime.md            # boot, DI, pipeline, hosted services / app bootstrap
  domain.md             # areas de negocio / proposito
  conventions.md        # regras praticas de mudanca e teste
  patterns.md           # padroes locais observados
  tech-debt.md          # divida e prioridades (inclui gaps vs guideline)
```

Pastas extras so com volume:
- `flows/` se houver >1 fluxo operacional relevante
- `screens/` (ou equivalente) em front/mobile com multiplas areas de UI

Arquivo ou pasta so existe com conteudo. `index.md` mapeia “quando ler o que”.

## 5) Skills condicionais

Done when: cada skill no AGENTS tem evidencia no checkout, e cada skill sem evidencia foi omitida.

Espelhar o ponteiro do guideline (secao 2) no `AGENTS.md` e em `references/index.md`.

### Integracoes / hubs / messaging

Se o repositorio for API ou hub (`dominio=api` ou `integracoes`, ou evidencia de consumer/producer — inbox, assinaturas, fila, topico/evento/entidade/versao):

- Incluir no `AGENTS.md` (tabela e regras rapidas) e espelhar em `references/index.md` + `conventions.md` a Domain Skill do time **somente se existir e houver evidencia** (`references/domain-skills.md`).
- A Domain Skill e a fonte operacional do produto; o AGENTS so aponta.

Caso contrario: omitir.

### Outras Domain Skills e skills de framework

| Condicao no checkout | Skill |
|---|---|
| Lib/auth/UI kit interna (package/import comprovado) | Domain Skill local do time (fora do Nero) |

| Servidor ou consumidor MCP | `$nero` + guideline mcp |
