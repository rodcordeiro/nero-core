Use obrigatoriamente a skill $nero e o MCP `nero-knowledge-base` como caminho preferencial de consulta, grafo e registro. Leia `references/mcp-tools.md` e `references/knowledge-routing.md` antes de registrar. Campos, vocabulario de `links:` e git via MCP vivem nessas references — este playbook e o roteiro.

Objetivo:
Revisar a aplicacao `<NOME_DO_PROJETO>` (dominio primario: `<api|front|mobile|integracoes|powershell|mcp>`) e atualizar o Knowledge Repo (Markdown sob `KnowledgeRoot__Path`) sem duplicar notas.

Premissas:
- Markdown no Knowledge Repo e canonico; o SQLite deriva o grafo no reindex (`nero_admin_reindex`), responsabilidade do cliente apos o lote.
- O path `skills/nero/knowledge/` nao e canonico — use o Knowledge Repo configurado.
- Checkout da aplicacao: leitura obrigatoria; contexto MCP nao substitui evidencia de codigo. Codigo da aplicacao permanece intacto.
- Registrar so o comprovado; evidencia fraca → hipotese (snapshot) ou omitir.
- Secrets, tokens, cookies, Authorization Bearer, URLs/payloads sensiveis, PII e valores reais de ambiente ficam fora das notas.

Placeholders:
- `<NOME_DO_PROJETO>` — ex.: `Acme.Api`
- `<KNOWLEDGE_REPO>` — root local do Knowledge Repo (`KnowledgeRoot__Path`)
- `<REPOSITORIO_DA_APP>` — checkout da aplicacao sob revisao

---

## 1) Sync e contexto da aplicacao

Done when: Knowledge Repo atualizado (ff-only ou `nero_admin_git_pull`) e o mapa factual do app (README, AGENTS, stack, fronteiras) esta citado com paths.

1. `git -C <KNOWLEDGE_REPO> pull --ff-only` (stash/commit local antes; preferir `nero_admin_git_*`).
2. Ler README, AGENTS.md (se existir), docs e configs principais no checkout da app.
3. Mapear stack, modulos, fronteiras, integracoes, autenticacao, observabilidade, testes e pipeline.

---

## 2) Consultar knowledge existente (MCP primeiro)

Done when: health + context + search + related foram executados (ou fallback filesystem documentado), e a estrutura base do projeto existe.

Ordem:

1. `nero_admin_status` se a sessao parecer inconsistente.
2. Fila multi-projeto: `nero_admin_ecosystem_health` primeiro.
   - Priorizar `projectsWithIssues` com `MissingRecentSnapshot` / `StaleSnapshot`.
   - Este arquivo ja e o playbook: para cada projeto da fila, execute as secoes seguintes com aquele nome (e dominio quando conhecido). Issues estruturais (`MissingIndex`, `MissingContext`, …) depois do frescor.
3. `nero_admin_project_health` com `project=<NOME_DO_PROJETO>` e `primaryDomain=<dominio>`.
   - Inspecionar `hasRecentSnapshot`, `latestSnapshotDate`, `latestSnapshotAgeDays`.
   - Entrada por health (`MissingRecentSnapshot` / `StaleSnapshot`): a `recommendation` aponta este path; continue as secoes seguintes. Entrada pelo indice (review geral): o health informa frescor; execute o fluxo completo mesmo com snapshot recente.
4. `nero_get_project_context` (`includeDecisions=true`, `includeTroubleshooting=true`): `activeDecisions` vigentes; `supersededDecisions` historico.
5. `nero_get_domain_context` do dominio primario (`includeProjects=true`).
6. `nero_search_knowledge` para precedentes, nomes antigos, sinonimos e debitos ja registrados.
7. `nero_find_related_knowledge` com `project` e/ou `topic` (`relationTypes` quando util).
8. Fallback: leitura direta em `<KNOWLEDGE_REPO>/` se o MCP falhar ou divergir do filesystem.

Se `exists=false` ou health indicar ausencia de estrutura base: `nero_register_project` **antes** de qualquer outra nota.

---

## 3) Revisar a aplicacao (somente leitura)

Done when: cada achado abaixo tem path/trecho de evidencia, ou foi omitido de proposito.

Analise de checkouts pode ser paralela entre apps; escrita no knowledge (secao 5+) e **serial**.

Mapear:
- regras de negocio (rotas, services, validators, DTOs, telas, hooks, jobs, consumers);
- padroes reutilizaveis;
- contratos publicos (endpoints, eventos, filas, payloads sanitizados, status codes, authz);
- integracoes e dependencias externas;
- conhecimentos tribais (arquivo/trecho como evidencia);
- debitos, riscos, acoplamentos, fragilidades e lacunas de teste.

---

## 4) Classificar escopo (`escopo` das tools)

Done when: cada nota planejada tem camada + `escopo`/path.

| Camada | Quando usar | `escopo` / path |
|---|---|---|
| Projeto | Especifico da aplicacao | `escopo=project` + `projeto=<NOME>` → `projects/<NOME>/` |
| Dominio | Orienta outros projetos do mesmo dominio | `escopo=domain` + `dominio=<api\|front\|mobile\|integracoes\|powershell\|mcp>` |
| Global | Vale para >1 dominio ou convencao ampla | `escopo=global` |

Camada mais especifica; promover so com evidencia de reuso (`references/knowledge-routing.md`).

---

## 5) Tipo de conhecimento → tool MCP

Done when: cada achado tem uma tool (ou edicao da nota vigente), o lote e serial, e search/related confirmaram nota vigente vs nota nova.

Registrar via `nero_register_*` / `nero_update_project_*`, uma escrita por vez. Markdown direto so se o MCP falhar; templates do Knowledge Repo e o mesmo vocabulario de `links:`. Campos minimos: `references/mcp-tools.md`.

| Achado | Tool |
|---|---|
| Projeto inexistente / sem base | `nero_register_project` |
| Dominio novo | `nero_register_domain` |
| Atualizar / reativar dominio | `nero_update_domain` |
| Inativar dominio | `nero_inactivate_domain` |
| Index / context / inventory do projeto | `nero_update_project_index` / `nero_update_project_context` / `nero_update_project_inventory` |
| Regra de negocio comprovada | `nero_register_business_rule` |
| Decisao / mudanca de orientacao | `nero_register_decision` (`supersedes` se substitui decision antiga) |
| Padrao reutilizavel | `nero_register_pattern` |
| Validacao / teste / criterio de aceite | `nero_register_validation_rule` |
| Inventario, tribal knowledge, debito observado | `nero_register_snapshot` |
| Incidente / troubleshooting | `nero_register_troubleshooting` |

Roteamento:
- contexto / inventario → `nero_update_project_*` (bootstrap com `nero_register_project`); evidencia longa → snapshot;
- tribal → snapshot (ou pattern/decision se for regra/orientacao estavel);
- debito → snapshot; se houver tratamento acordado, decision;
- complementar nota vigente → editar a nota no filesystem (register cria nota nova);
- mudanca de orientacao → **nova** decision com `supersedes`; `updates` e evolucao entre notas, nao substitui decision.

Anti-duplicacao:
1. `nero_search_knowledge` + `nero_find_related_knowledge` + health/context.
2. Equivalente existente → complementar a vigente.
3. Orientacao mudou → nova decision com `supersedes`; a antiga permanece historico.

## 6) Relacoes

Done when: cada nota de conteudo do lote tem `links:` nao vazio no vocabulario preferencial.

Vocabulario, mapeamento de campos e regras do grafo: `references/knowledge-routing.md` e `references/mcp-tools.md`.

Relacao canonica: writer ou edicao de `links:` no Markdown. `nero_link_knowledge` so para edge manual entre nodes **ja indexados** (SQLite, sem frontmatter). Informe `evidence` curta. Relacao por coocorrencia, pasta ou data fica de fora.

---

## 7) Seguranca na escrita

Done when: exemplos, logs e evidencias citam arquivos/comportamentos, com placeholders da allowlist.

Sanitizar contratos, logs e troubleshooting. Checklist: `references/compliance-security.md`.

---

## 8) Validar antes de concluir

Done when: `nero_admin_validate` retorna `isValid=true` e `isCompliant=true`, e `diff --check` (ou `nero_admin_git_status`) esta limpo.

Writers gravam Markdown. Apos o lote, execute o checklist em `references/workflow.md` e `references/compliance-security.md` (`nero_admin_reindex` uma vez, depois `nero_admin_validate`). Search/context/related de notas recem-gravadas depois do reindex.

---

## 9) Commit e push (somente se houver alteracao no Knowledge Repo)

Done when: commit (e push, se pedido) cobre so paths de knowledge allowlisted, ou a secao foi omitida porque o diff estava vazio.

Preferir `nero_admin_create_commit` + `nero_admin_git_push`. Mensagem: `knowledge: review <NOME_DO_PROJETO>`. Gates e fallback shell: `references/compliance-security.md`.

---

## 10) Resumo final

Done when: os 10 itens abaixo citam paths/tools/resultados reais deste run (ou “omitido” com motivo).

Informar:
1. aplicacao revisada e dominio;
2. contexto MCP usado (health, project_context, domain_context, searches, related);
3. areas/arquivos principais analisados no repo da app;
4. notas criadas/atualizadas/superseded (paths + tools);
5. regras de negocio registradas;
6. padroes registrados (`source_for` / reuso);
7. snapshots de tribal knowledge / inventario / debitos;
8. troubleshooting/decisions relevantes;
9. validacoes (`reindex`, `validate.isValid` / `isCompliant`, `diff --check`, commit/push);
10. lacunas, hipoteses e o que foi conscientemente ignorado.
