Use obrigatoriamente a skill $nero e o MCP `nero-knowledge-base` como caminho preferencial de consulta, grafo e registro. Leia `references/mcp-tools.md` e `references/knowledge-routing.md` antes de registrar.

Objetivo:
Revisar a aplicação `<NOME_DO_PROJETO>` (domínio primário: `<api|front|mobile|integracoes>`) e atualizar o Knowledge Repo (Markdown sob `KnowledgeRoot__Path`) sem duplicar notas e respeitando o contrato de notas/relações do MCP.

Premissas:
- Markdown no Knowledge Repo é canônico; o SQLite deriva o grafo no reindex (`nero_admin_reindex`), que é responsabilidade do cliente após o lote de escritas.
- O path `skills/nero/knowledge/` **não** é canônico no produto Nero — use o Knowledge Repo configurado.
- Não alterar código da aplicação.
- A leitura do filesystem do repo da aplicação é obrigatória para validar código de produto; contexto MCP não substitui essa evidência.
- Não inventar regra de negócio: sem evidência conclusiva, registrar como hipótese (snapshot) ou omitir.
- Nunca registrar credenciais, tokens, cookies, Authorization Bearer, URLs sensíveis, payloads sensíveis, PII ou valores reais de ambiente.

Placeholders:
- `<NOME_DO_PROJETO>` — ex.: `Acme.Api`
- `<KNOWLEDGE_REPO>` — root local do Knowledge Repo (`KnowledgeRoot__Path`)
- `<REPOSITORIO_DA_APP>` — checkout da aplicação sob revisão

---

## 1) Sync e contexto da aplicação

1. `git -C <KNOWLEDGE_REPO> pull --ff-only` (se houver mudanças locais, stash/commit antes; não forçar rebase). Preferir tools `nero_admin_git_*` quando disponíveis.
2. Ler contexto essencial do repo da aplicação: README, AGENTS.md (se existir), docs relevantes e configs principais.
3. Mapear stack, módulos, fronteiras, integrações, autenticação, observabilidade, testes e pipeline — sem editar código.

---

## 2) Consultar knowledge existente (MCP primeiro)

Ordem obrigatória:

1. `nero_admin_status` (opcional, se a sessão parecer inconsistente).
2. Em triage multi-projeto (fila de reviews): `nero_admin_ecosystem_health` primeiro.
   - Priorizar `projectsWithIssues` com `MissingRecentSnapshot` / `StaleSnapshot`.
   - Para cada um, carregar o path do playbook na `recommendation` do issue e executar este fluxo com o nome do projeto (e domínio quando conhecido).
   - Em seguida tratar issues estruturais (`MissingIndex`, `MissingContext`, etc.).
3. `nero_admin_project_health` com `project=<NOME_DO_PROJETO>` e `primaryDomain=<dominio>`.
   - Inspecionar `hasRecentSnapshot`, `latestSnapshotDate`, `latestSnapshotAgeDays` e issues de frescor interno.
   - Se `hasRecentSnapshot=false` (issues `MissingRecentSnapshot` / `StaleSnapshot`), a `recommendation` aponta este playbook (`skills/nero/prompts/knowledge-review-app-mcp.txt`); carregar o arquivo e executar o fluxo com o projeto/dominio informados — nao esperar o texto do prompt embutido na recommendation.
4. `nero_get_project_context` com `includeDecisions=true` e `includeTroubleshooting=true`.
   - Usar `activeDecisions` como orientação vigente.
   - Tratar `supersededDecisions` apenas como histórico (via `supersedes`).
5. `nero_get_domain_context` para o domínio primário (`includeProjects=true`).
6. `nero_search_knowledge` para precedentes, nomes antigos, sinônimos e débitos já registrados.
7. `nero_find_related_knowledge` com `project` e/ou `topic`, filtrando `relationTypes` quando útil (`related_pattern`, `related_decision`, `belongs_to_domain`, etc.).
8. Fallback: leitura direta em `<KNOWLEDGE_REPO>/` se o MCP falhar ou estiver desalinhado do filesystem.

Se `exists=false` ou health indicar ausência de estrutura base: registrar projeto **antes** de qualquer outra nota.

---

## 3) Revisar a aplicação (somente leitura)

Mapear com evidência concreta no código. A análise de checkouts pode ser paralela entre apps; **não** escrever knowledge em paralelo — o lote de registro (seção 5+) é serial.

- regras de negócio (rotas, services, validators, DTOs, telas, hooks, jobs, consumers);
- padrões reutilizáveis;
- contratos públicos (endpoints, eventos, filas, payloads sanitizados, status codes, authz);
- integrações e dependências externas;
- conhecimentos tribais inferidos (com arquivo/trecho como evidência);
- débitos técnicos, riscos, acoplamentos, fragilidades e lacunas de teste.

Não inventar regra: evidência fraca → hipótese explícita ou não registrar.

---

## 4) Classificar escopo (`escopo` das tools)

| Camada | Quando usar | `escopo` / path |
|---|---|---|
| Projeto | Específico da aplicação | `escopo=project` + `projeto=<NOME>` → `projects/<NOME>/` |
| Domínio | Orienta outros projetos do mesmo domínio | `escopo=domain` + `dominio=<api\|front\|mobile\|integracoes>` |
| Global | Vale para >1 domínio ou convenção ampla do ecossistema | `escopo=global` |

Preferir a camada mais específica; promover só com evidência de reuso.

---

## 5) Tipo de conhecimento → tool MCP (obrigatório)

Registrar via `nero_register_*` / `nero_update_project_*`, em lote **serial** (uma escrita por vez no knowledge). Escrita manual em Markdown só se o MCP estiver indisponível/falhar; nesse caso usar templates do Knowledge Repo (ou scaffold) e o mesmo vocabulário de `links:`.

Análise de repositórios de produto pode continuar em paralelo; consolidar e gravar knowledge só depois, em sequência.

| Achado | Tool | Campos mínimos |
|---|---|---|
| Projeto inexistente / sem base | `nero_register_project` | `projeto`, `dominio` (ativo), `proposito`, `origem` |
| Registrar dominio novo | `nero_register_domain` | `dominio`, `proposito`, `origem` (+ `arquivos`) |
| Atualizar / reativar dominio | `nero_update_domain` | `dominio`, `proposito`, `arquivos` (+ `reativar` se inactive; `sourceFor` omitido preserva links) |
| Inativar dominio | `nero_inactivate_domain` | `dominio`, `motivo`, `origem` (+ `confirmacao`/`evidencia` se houver projetos) |
| Atualizar index do projeto | `nero_update_project_index` | `projeto`, `dominio`, `proposito`, `arquivos` (+ `origem`) |
| Atualizar context do projeto | `nero_update_project_context` | `projeto`, `dominio`, `proposito`, `stack`, `superficie`, `resumoOperacional` (+ `skillOperacional`, `origem`) |
| Criar/atualizar inventory do projeto | `nero_update_project_inventory` | `projeto`, `dominio`, `revisadoEm`, `classificacao`, `sinaisTecnicos` (+ git/origem) |
| Regra de negócio comprovada | `nero_register_business_rule` | `titulo`, `escopo`, `regra`, `evidencia`, `origem` (+ `projeto`/`dominio`) |
| Decisão técnica / mudança de orientação | `nero_register_decision` | `titulo`, `escopo`, `problema`, `opcoes`, `decisao`, `consequencias`, `origem`; se substitui decisão antiga: `supersedes=[path/id da decision]` |
| Padrão reutilizável | `nero_register_pattern` | `titulo`, `escopo`, `contexto`, `padrao`, `quandoAplicar`, `quandoNaoAplicar`, `origem`; opcional `usadoPor`, `candidatoParaReuso`, `exemplos`, `excecoes` |
| Validação / teste / critério de aceite | `nero_register_validation_rule` | `titulo`, `escopo`, `regra`, `criterio`, `evidencia`, `origem`; opcional `lacunasConhecidas` |
| Inventário técnico, snapshot pontual, tribal knowledge com evidência, débito técnico observado | `nero_register_snapshot` | `titulo`, `escopo`, `contexto`, `evidencia`, `origem`; opcional `relacionadoA`, `evidenciaDe` |
| Incidente / troubleshooting | `nero_register_troubleshooting` | `titulo`, `escopo`, `sintoma`, `causa`, `acao`, `evidencia`, `impacto`, `origem`; opcional `solucao`, `prevencao`, `causadoPor`, `relacionadoA` |

Mapeamento semântico:

- “contexto do projeto / inventário” → `nero_update_project_context` e/ou `nero_update_project_inventory` (bootstrap com `nero_register_project` se faltar base); evidencia longa → `nero_register_snapshot`;
- “conhecimentos tribais” → `snapshot` (ou `pattern`/`decision` se for regra/orientação estável);
- “débitos técnicos” → `snapshot` (estado observado) e, se houver decisão de tratamento, `decision`;
- “complementar nota vigente” → editar a nota existente no filesystem (MCP register cria nota nova; não duplicar por título/sinônimo);
- “mudança de orientação” → **nova** `decision` com `supersedes` apontando para a decision antiga (nunca `updates` no lugar de `supersedes`).

Anti-duplicação antes de registrar:

1. `nero_search_knowledge` + `nero_find_related_knowledge` + health/context.
2. Se já existir nota equivalente: complementar a vigente; não criar clone.
3. Se a orientação mudou: nova decision com `supersedes`; preservar a antiga como histórico.

## 6) Contrato de relações (vocabulário preferencial)

As tools `nero_register_*` emitem `links:` preferenciais. Não inventar tipos. Não usar legado.

Vocabulário permitido:

- `belongs_to_domain` — projeto/nota → domínio primário
- `documents` — nota documenta/contextualiza alvo
- `evidences` — snapshot → **nota concreta com slug** (nunca hub: `index`, `context`, `domains/*/patterns`, `projects/*/decisions`)
- `updates` — evolução entre notas (não usar para substituir decision)
- `depends_on` — dependência comprovada; orientação **consumer → backend**
- `uses_backend` — front/mobile → API/lib
- `related_decision` / `related_pattern` — ligação semântica direta
- `source_for` — pattern/fonte → consumidores (`usadoPor` no register)

Especial (allowlist estreita):

- `supersedes` — **somente decision → decision**. Não colapsar em `updates`.

Proibido (validate rejeita): `relates_to`, `caused_by`, `used_by`, `candidate_for_reuse` e qualquer tipo fora da lista.

Mapeamento dos campos de link das tools:

| Campo da tool | Edge emitida |
|---|---|
| `pattern.usadoPor` | `source_for` |
| `pattern.candidatoParaReuso` | `documents` / `related_pattern` / `related_decision` (conforme path do alvo) |
| `snapshot.relacionadoA` | `documents` |
| `snapshot.evidenciaDe` | `evidences` (somente nota concreta) |
| `troubleshooting.causadoPor` | `related_decision` ou `documents` |
| `troubleshooting.relacionadoA` | `related_pattern` / `related_decision` / `documents` |
| `decision.supersedes` | `supersedes` |
| business/validation/decision (mínimo por escopo) | `documents` (+ `belongs_to_domain` se houver domínio) |

`nero_link_knowledge`:

- usar só para edge manual idempotente entre nodes **já indexados**;
- **não** altera frontmatter Markdown;
- preferir `nero_register_*` (ou edição do `links:` no Markdown) para relação canônica;
- sempre informar `evidence` curta e comprovada;
- não criar link por coocorrência, mesma pasta ou proximidade temporal.

Regras de qualidade do grafo:

- notas de conteúdo precisam de `links:` não vazio;
- sem `depends_on` para o próprio projeto;
- sem `depends_on`/`uses_backend` invertidos (API → Front/Mobile);
- sem `evidences` para hubs;
- domínio primário do repo em `belongs_to_domain`; `integracoes` só como segundo domínio quando for API/barramento central de integração.

---

## 7) Segurança na escrita

- Sanitizar exemplos de contratos, logs e troubleshooting.
- Não expor valores reais de ambiente.
- Evidências devem citar arquivos/comportamentos, não segredos.

---

## 8) Validar antes de concluir

`nero_register_*` / `nero_update_project_*` apenas gravam Markdown; **não** reindexam. Após concluir o lote de criações/edições de knowledge:

1. `nero_admin_reindex` (uma vez, no fim do lote — responsabilidade do cliente)
2. `nero_admin_validate` → `isValid` e `isCompliant` devem ser `true` (obrigatório antes do commit). Se so compliance falhar, use `nero_admin_compliance_scan` para triage/quarentena.
3. Opcional: `nero_admin_check_index_consistency` se houver suspeita MCP ↔ filesystem
4. Conferir ausência de duplicação óbvia e links quebrados
5. `git -C <KNOWLEDGE_REPO> diff --check` (ou `nero_admin_git_status`)

Não confiar em `search`/`find_related`/`get_*_context` para notas acabadas de gravar antes do reindex. Não commitar se `nero_admin_validate` falhar.

---

## 9) Commit e push (somente se houver alteração no Knowledge Repo)

Preferir `nero_admin_create_commit` + `nero_admin_git_push` quando disponíveis. Fallback shell:

```text
git -C <KNOWLEDGE_REPO> add .
git -C <KNOWLEDGE_REPO> commit -m "knowledge: review <NOME_DO_PROJETO>"
git -C <KNOWLEDGE_REPO> push
```

Não incluir `*.db`, segredos ou arquivos fora do corpus Markdown sem necessidade. Stage apenas paths de knowledge/docs allowlisted.

---

## 10) Resumo final obrigatório

Informar:

1. aplicação revisada e domínio;
2. contexto MCP usado (`project_context`, `domain_context`, searches, related, health);
3. áreas/arquivos principais analisados no repo da app;
4. notas criadas/atualizadas/superseded (paths + tools usadas);
5. regras de negócio registradas;
6. padrões registrados (`source_for` / reuso quando houver);
7. snapshots de tribal knowledge / inventário / débitos;
8. troubleshooting/decisions relevantes;
9. validações (`reindex`, `validate.isValid`, `diff --check`, commit/push);
10. lacunas, hipóteses e o que foi conscientemente ignorado.
