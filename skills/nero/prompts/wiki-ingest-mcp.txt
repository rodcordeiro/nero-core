Use obrigatoriamente a skill $nero e o MCP nero-knowledge-base quando disponivel. Leia `references/mcp-tools.md` e `references/knowledge-routing.md` antes de registrar. Campos, vocabulario de `links:` e git via MCP vivem nessas references — este playbook e o roteiro.

Fluxo de ingestao de wiki/Markdown externo → Knowledge Repo.

Placeholders:
- `<WIKI_REPO>` — checkout local da wiki ou fonte Markdown (pull/ff-only antes de ler)
- `<KNOWLEDGE_REPO>` — root do Knowledge Repo (`KnowledgeRoot__Path`)
- `<NOME_DO_PROJETO>` — nome canonico no knowledge (ex.: `Acme.Billing.Api`)

1. Identifique o intervalo.
   Done when: lista de paths Markdown added/modified/renamed (deletes so se indicarem decision/regra superseded).
   - `git -C <WIKI_REPO> pull --ff-only`;
   - considere adicionados, modificados ou renomeados.

2. Leia so os Markdown desse intervalo com valor reutilizavel.
   Done when: cada arquivo lido foi classificado (ingerir / descartar) e a origem cita o path relativo da wiki.
   - Descarte transitorio, duplicado, incompleto ou puramente operacional.
   - Secrets, tokens, cookies, Authorization Bearer, URLs/payloads sensiveis, connection strings, PATs, webhooks secretos e dados sigilosos ficam fora das notas; origem sem query strings nem trechos sensiveis.

3. Extraia conhecimento reutilizavel e classifique o tipo MCP.
   Done when: cada trecho ingerido tem exatamente uma tool `nero_register_*`.
   - regra de negocio → `nero_register_business_rule`;
   - decisao tecnica → `nero_register_decision`;
   - padrao de implementacao → `nero_register_pattern`;
   - validacao/teste/criterio de aceite → `nero_register_validation_rule`;
   - incidente/troubleshooting → `nero_register_troubleshooting`;
   - evidencia pontual/inventario/diagnostico versionado → `nero_register_snapshot`;
   - contratos, eventos ou integracoes: pattern, decision ou business_rule conforme o conteudo; estado observado → snapshot com `evidenciaDe` para a nota concreta.

4. Classifique o escopo MCP.
   Done when: cada nota tem `escopo` + campos auxiliares, e o projeto existe no knowledge.
   - `project` + `projeto`: `<NOME_DO_PROJETO>` → `projects/<projeto>/`;
   - `domain` + `dominio`: `api|front|mobile|integracoes|powershell|mcp` → `domains/<dominio>/`;
   - `global` → `global/`;
   - projeto ausente: `nero_admin_project_health` e, se preciso, `nero_register_project` antes de qualquer outra nota.

5. Consulte o knowledge existente (MCP primeiro).
   Done when: search + context (projeto/dominio) + related rodaram, ou o fallback filesystem foi documentado.
   - `nero_search_knowledge` (sinonimos, titulos, nomes antigos);
   - `nero_get_project_context` quando houver projeto (`activeDecisions` vigentes; `supersededDecisions` historico);
   - `nero_get_domain_context` quando o escopo for de dominio;
   - `nero_find_related_knowledge` antes de criar regra/padrao/decisao nova;
   - fallback: busca em `<KNOWLEDGE_REPO>/` se o MCP estiver indisponivel.

6. Atualize a nota vigente ou ligue a evolucao.
   Done when: cada item e complemento da vigente, nova decision com `supersedes`, ou nota nova ligada com `updates` — um significado, um path.
   Vocabulario e mapeamento de campos: `references/knowledge-routing.md` e `references/mcp-tools.md`.
   - mudanca de orientacao em decisao: nova `nero_register_decision` com `supersedes: [<id-ou-path da decision antiga>]` (somente decision→decision);
   - evolucao de padrao/regra/troubleshooting/snapshot: completar a vigente; nota nova liga com `updates`;
   - `evidences` / `evidenciaDe` → nota concreta com slug;
   - `depends_on` / `uses_backend`: consumer → backend.

7. Registre no Knowledge Repo.
   Done when: o lote serial usou `nero_register_*` (ou fallback documentado), cada nota de conteudo tem `links:` nao vazio, e `origem` cita a wiki sanitizada.
   - escrita direta em `<KNOWLEDGE_REPO>/` so como fallback; templates do Schema/scaffold;
   - relacao canonica: `links:` no Markdown via writer; `nero_link_knowledge` so para edge entre nodes ja indexados.

8. Valide antes de concluir.
   Done when: `nero_admin_validate` retorna `isValid=true` e `isCompliant=true`, e `diff --check` (ou `nero_admin_git_status`) esta limpo.
   Execute o checklist em `references/workflow.md` e `references/compliance-security.md` (`nero_admin_reindex` uma vez, depois `nero_admin_validate`).

9. Se houver alteracoes no Knowledge Repo:
   Done when: commit (e push, se pedido) cobre so paths allowlisted, ou a secao foi omitida porque o diff estava vazio.
   Preferir `nero_admin_create_commit` + `nero_admin_git_push`. Mensagem: `knowledge: ingest wiki`. Gates e fallback shell: `references/compliance-security.md`.

10. Resumo final.
    Done when: os itens abaixo citam paths/tools/resultados reais deste run (ou “omitido” com motivo).
    - intervalo processado;
    - arquivos da wiki lidos;
    - notas criadas, atualizadas ou superseded (ids/paths e relacoes);
    - tools MCP usadas;
    - resultado de `nero_admin_validate` / reindex;
    - lacunas ou informacoes ignoradas (incluindo material sensivel descartado).
